# Concurrent relational upserts

## Context

A REST `PUT` or `PATCH` with a caller-supplied primary key performs an upsert. The SQL Server, PostgreSQL, and Data Warehouse SQL builders currently decide between `UPDATE` and `INSERT` using more than one database operation. At `READ COMMITTED`, two requests for the same missing key can both choose the insert path.

The database policy behavior must remain unchanged:

- An existing row is updated only when the update policy matches.
- An existing row that fails the update policy must not fall through to insert.
- A missing row is inserted only when the create policy matches.
- The response still identifies whether the request inserted or updated the row.

MySQL and Cosmos DB are outside the scope of this change.

## Correctness requirements

1. Upserts targeting the same source and primary-key value are serialized before checking whether the row exists.
2. A waiter checks existence only after the preceding transaction commits or rolls back.
3. The serialization primitive is held through the ambient upsert transaction.
4. Upserts for different keys should remain concurrent where the provider can support key-level locking.
5. Lock cleanup must be automatic on commit, rollback, cancellation, and exceptions.
6. Existing policy, trigger, view, composite-key, and fallback-to-update behavior must remain intact.
7. The isolation level of unrelated mutations must not be raised globally.

## Design

### SQL Server

The initial primary-key existence query uses `WITH (UPDLOCK, HOLDLOCK)`.

- `UPDLOCK` makes concurrent writers request incompatible update locks.
- `HOLDLOCK` gives the read serializable semantics through transaction completion, including a key-range lock when the requested key is absent.
- The existing ambient transaction keeps the lock across the subsequent `UPDATE` or `INSERT`.
- The hint is attached only to the initial decision read; the result-set contract is unchanged.

This is preferred over `MERGE`, which would substantially complicate existing trigger and database-policy handling.

### PostgreSQL

PostgreSQL row locks cannot lock a row that does not exist. Each upsert therefore first obtains a transaction-level advisory lock:

```sql
SELECT pg_advisory_xact_lock(
    hashtextextended(jsonb_build_array(schema, source, primary_key_values...)::text, 0)
) AS upsert_lock;
```

The lock key contains the schema, source name, and every primary-key value. Hash collisions only serialize unrelated upserts; they cannot allow same-key upserts to overlap.

The lock is deliberately acquired in a separate statement before the existence query. Under PostgreSQL `READ COMMITTED`, a statement receives its snapshot when that statement begins. If lock acquisition and existence checking shared one statement, a waiter could resume with the snapshot taken before the preceding transaction committed. A separate existence statement receives a fresh snapshot after the lock is granted.

The PostgreSQL executor consumes and validates the lock result set before reading the existing count and mutation result sets. Transaction-level advisory locks are released automatically with the ambient transaction.

This preserves support for the existing update-first CTE, database policies, and updatable views. Replacing it with `INSERT ... ON CONFLICT` would make create-policy evaluation and view support materially more complex.

### Data Warehouse SQL

Data Warehouse SQL sources can be heaps or columnstore tables without an enforced unique key. A key-range lock therefore cannot be assumed. The initial existence read uses `WITH (TABLOCKX, HOLDLOCK)` when an insert fallback is possible.

This conservatively serializes upserts for the source table and prevents duplicate logical keys even when the warehouse does not enforce the configured DAB key fields. Update-only fallback operations retain the existing read behavior because they cannot create a duplicate.

The broader lock is an intentional correctness tradeoff for a provider that cannot guarantee an indexed unique key.

### Update-only fallback

An upsert falls back to update-only behavior when it cannot safely construct an insert, including autogenerated primary keys and `PATCH` requests that omit required columns.

- SQL Server retains its key-level lock because it also serializes updates to an existing key.
- PostgreSQL retains its advisory lock and result-set contract for a uniform execution path.
- Data Warehouse SQL does not take the exclusive table lock because this path cannot insert a duplicate.

## Test strategy

### SQL generation tests

Tests construct a composite-key `SqlUpsertQueryStructure` and verify that:

- SQL Server places `UPDLOCK, HOLDLOCK` on the existence read before the branch decision.
- PostgreSQL acquires a transaction advisory lock before the existence read.
- The PostgreSQL lock key includes the source identity and every primary-key parameter, but excludes non-key parameters.
- Data Warehouse SQL uses a held exclusive table lock when insert fallback is possible and does not add it to update-only fallback queries.
- Existing update-policy predicates remain in the update branch.

### Integration tests

SQL Server and PostgreSQL REST tests issue several same-key upserts concurrently. They require:

- exactly one `201 Created` response;
- all remaining responses to be `200 OK`;
- no conflict or server-error responses; and
- exactly one persisted row for the logical key.

Both `PUT` and `PATCH` paths are covered because they share the builder but populate update operations differently.

Data Warehouse SQL is covered at SQL-generation level in the existing SQL Server-backed test pipeline. That pipeline does not execute against a real dedicated SQL pool and its schema intentionally has no physical primary-key constraint, so the generated `TABLOCKX` contract is the portable behavior under test.

A real dedicated-pool concurrency test should be added when that infrastructure is available; the current pipeline cannot validate provider-specific runtime lock behavior.

## Operational considerations

- Same-key requests may wait for the prior request rather than fail with a uniqueness violation.
- SQL Server and PostgreSQL retain concurrency across different keys, subject to normal lock escalation and rare advisory-hash collisions.
- Data Warehouse SQL serializes insert-capable upserts per source table.
- Existing transaction timeout and cancellation behavior remains authoritative; no unbounded application-level lock state is introduced.
