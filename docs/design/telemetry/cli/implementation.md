# CLI telemetry implementation note

This is a **maintainer-oriented implementation note**, not a public/stable API specification, a requirements approval document or privacy/CELA approval. It describes the current synthetic-only implementation and its validation boundaries.

## Boundaries

This implementation adds CLI collection to the existing engine telemetry foundation, preserving the supported Azure Monitor exporter dependency, destination gate, privacy guard, API identity format and finite delivery behavior. Production collection remains off. The public [field and validation guide](../../../telemetry.md) describes the current emitted contract and the required linkability review.

| Boundary | Responsibility |
| --- | --- |
| Enablement | Check the single `DAB_TELEMETRY_OPT_OUT` veto, synthetic opt-in, both SDK-statistics opt-outs and explicit valid product routing before identity/notice/sender work. No CLI-specific opt-out or process-global SDK workaround is added. |
| Invocation | The CLI entry point owns one invocation session; its dispatch wrapper completes it once around the real parse and handler. Public `Execute` does not implicitly create a CLI session. |
| Grammar | Apply the reviewed command/option allowlist and pinned parser's token rules. The actual parse determines control requests and success/failure. No raw argument survives inspection. |
| Installation | Safely persist a per-user-profile random UUID where supported. Only the atomic publication winner records first-run initialization. Unavailable storage omits identity, not useful command telemetry. |
| Configuration | Lookups cannot create state. Successful `init` resolves identity only after writing. Later commands observe the exact root already selected by their normal work; no extra configuration discovery. |
| Provider category | Project a closed enum from the already loaded or successfully written model. No raw option values, connection strings, configuration serialization, additional loads or identity I/O are used. |
| Command configuration context | Bound the model and reuse the engine's configured/effective vocabulary. Retain only an immutable categorical JSON string in the command event; no engine epoch or separate event is invented. |
| Handoff | Carry separate parent/engine session IDs, available installation/API identities and a closed launch source, without paths, arguments, callbacks or mutable global state. |
| Delivery | CLI and engine use the same generic bounded delivery algorithm and lease a serialized, process-owned SDK sender by normalized destination. No second ingestion protocol or customer logger is used. |

CLI, service, Core and MCP integration are coupled to assemblies from the **same DAB release**. The transport, destination validation, DataX mapping and sender pool are internal to Core; only the host-specific adapters remain in Service. Friend access is release-private, not a stable embedding API. Making implementation types public would not guarantee binary compatibility between mixed release versions.

MCP's packed Core dependency is exact, including prerelease versions. The pack target rejects mismatched project package versions, and the opt-in `TelemetryPackaging` tests inspect real package manifests for release and prerelease constraints. Core bundles its implementation dependencies; CLI tool distributions include their coordinated assemblies. Direct references that override the Core constraint can produce NuGet `NU1608`; suppressing it or manually mixing DLLs is unsupported.

## Sent-name alignment

Sent event families are `dab/cli.*` and `dab/engine.*`. The shared exporter adds `dab_` exactly once to top-level custom property keys. Command fields are therefore `dab_command`, `dab_subcommand`, `dab_control`, `dab_outcome`, `dab_failure_category`, `dab_duration_ms`, `dab_database_type`, `dab_option_*` and `dab_configuration_context`; the launch source is `dab_launch_source`. Context follows the same mapping, including `dab_os_family`, `dab_os_version`, `dab_architecture` and `dab_dotnet_version`. Existing `dab_` IDs and `dab_version` remain unchanged. Dots are preserved. Keys must be unique after prefixing and fit the 150-character ingestion limit; a collision or overlong key rejects the event rather than truncating it. Values and nested JSON keys are not rewritten. The public guide inventories all 82 top-level engine snapshot properties and the engine event-specific sent keys separately from CLI context.

The unchanged shared notice text is reproduced verbatim in [Enablement, notice and reset](../../../telemetry.md#enablement-notice-and-reset) as a **draft pending CELA review**, together with its per-invocation/direct-engine timing and linked-handoff deduplication rule. The [privacy-inventory rename ledger](../../../telemetry.md#privacy-inventory-rename-ledger) records the naming scope: no added telemetry fields, IDs or values, no bucket or duration changes, and no change to enablement, environment-selected routing, SDK prerequisites or the umbrella opt-out. No production/privacy approval or new live batch is implied.

## Ordering and lifecycle

1. Gate collection before profile state, notice and sender work. Show the notice on stderr before any send. Only a complete, valid same-process handoff skips the duplicate engine notice; every new enabled CLI invocation or direct engine run still shows it.
2. Initialize/reuse installation state. Emit `dab/cli.first_run` only for newly saved state.
3. Parse once and dispatch with an explicit invocation-owned session. Capture only approved option presence, never resolved defaults or values.
4. After successful configuration creation, allocate/reuse its API sidecar before `dab/cli.command`. Failed writes allocate none. Read-only/other commands perform lookup only.
5. At actual engine handoff, emit `dab/cli.engine_launch` and pass the selected engine ID before `dab/engine.process_started`. Same-run ephemeral API identity is preserved without claiming cross-invocation continuity.
6. Record command completion when the handler returns or an exception/cancellation is observed. Centralized typed return-code/exception classification preserves return codes, output and thrown exceptions. A typed engine-startup-failure observation distinguishes the web host's legacy normal return after `StopApplication` from actual successful initialization. Export carries a typed terminal result separately from recoverable attempt failures: no schema is a telemetry failure even when the legacy exit code is zero, while a successful retry is still success. A nonzero return without typed failure evidence remains `unknown`, never success or a guessed category.
7. Gracefully drain only the owning queue: 250 ms for ordinary CLI stop, two seconds for the engine, and an independent two seconds for each reserved helper. Parent stop does not join helper drains. Explicit disable discards without a final send.

With deferred MCP stdio initialization, an early handshake is not engine readiness. The first tool list/call initializes metadata and publishes the registry; only successful completion accepts the serving model and marks telemetry ready. Failures remain cached protocol errors and produce one startup-failure observation; normal shutdown still preserves its exit code. Protocol-only sessions emit neither readiness nor data-use milestones.

Host disposal has one owner: the web run path owns the web host, and the stdio helper owns the stdio host. The outer dispatch layer does not dispose either host a second time. Engine-failure observation uses the captured telemetry session, not a service lookup through an already disposed host.

Asynchronous export helpers own one-shot launch reservations. Reserving creates no identity, event, worker or sender. Actual preflight-approved handoff may occur after ordinary command completion/disposal, using its original parent session and a later sequence. Its separate capacity-one queue drains independently; parent CLI stop does not join it or extend the completed command's `dab_duration_ms`. Explicit disable revokes all such reservations. Cancellation before the helper runs, or failed preflight, never emits intent. No nested `start` command event is manufactured. Existing export serving/retry/cancellation semantics are unchanged.

The accepted configuration uses the actual CLI-selected root, including a generated merged root. Independent root sidecars are not assigned a common API ID, but the profile ID still permits cross-project linkage. There is no configuration hash or child-source identity. Ambiguous command targets omit API linkage. The engine rechecks root consistency when accepting configuration; direct starts have no parent CLI link.

All CLI events carry `dab_database_type` using the closed vocabulary in the public field guide. First-run precedes configuration work and remains `unknown`. Command classification observes the normally loaded model; a successful write replaces it with the saved provider, while rejected candidates and failed writes leave the loaded category unchanged. In particular, a provider-changing `configure` record clone must use its actual root `DataSource`, not the stale default entry in its internal merged map. Distinct known source providers yield `multiple`; identical providers do not. Only matching already loaded child records count as complete evidence, with a shared 256-node traversal budget. Unknown or ambiguous evidence is never repaired by additional discovery.

Each actual launch supplies its own preflight provider explicitly and snapshots it into the launch event. This remains true for an export helper after parent completion or normal stop/disposal: it cannot reuse mutable command state. The provider category does not extend the five-field engine bridge or add fields to engine events. The category describes configuration, not observed database usage, and does not replace option-presence flags.

Command failure-rate breakdowns cannot depend on a later engine snapshot or an API-sidecar identity. `dab_configuration_context` therefore accompanies every `dab/cli.command` outcome, using the same applicable configuration dimensions as engine snapshots. The one-property JSON representation still has 83 fixed nested keys and an 8,192-character limit, preserving the existing 128-property envelope and all 96 option-presence slots. Inside this JSON, the 82 snapshot keys retain their original unprefixed names, plus `observation`: `snapshot_schema=cli-configuration-v1` and `observation=loaded|saved|unknown` distinguish this evidence from an accepted engine configuration. Feature keys such as `runtime.rest.effective` also stay unprefixed; only the outer custom property is renamed. In Application Insights, read it with `parse_json(tostring(customDimensions.dab_configuration_context))["runtime.rest.effective"]`. No raw config serialization feeds this property.

Normal CLI dispatch establishes a scoped, default-off presence-capture permission. Existing config parsing can reuse the original bytes already read; child loaders inherit permission and an explicit engine policy overrides it. A disabled CLI cannot inherit an unrelated enabled scope. Capture caps (1 MiB characters/4,096 entities) lose optional provenance, never reject input or add discovery. Successful writes supply the already written JSON only for fresh structural presence, avoiding stale `with`-clone provenance; failed writes retain the loaded context. Projection checks matching loaded children and copies bounded dictionaries before using shared engine logic (256 configuration/source nodes, 256 references, depth 32, 4,096 model nodes). Unavailable input/projection remains explicitly unknown. Counts, enum values and configured/effective state semantics are the existing engine categories, not invented CLI defaults.

Ordinary configuration loads share one observation adapter: observe the already selected root, perform the existing load once with the caller's replacement policy, classify load rejection, and capture the loaded model. Diagnostics stay with the caller. Domain-specific failure hints remain at boundaries where a bool cannot identify the cause; they preserve first-failure semantics. Invocation-local launch/export overrides are grouped into immutable dependency objects, separate from the immutable telemetry handoff and parsed CLI options.

The session stores provider and configuration context together under versioned observation ownership. Projection runs outside the session lock; completion, disable and newer observations cannot wait for or be overwritten by an older projection. Only immutable closed categories enter delivery. First-run and launch events have no command configuration context, and a late helper cannot modify an already completed command.

Both identity stores retain atomic Linux no-replace publication through `renameat2(RENAME_NOREPLACE)` and Windows no-overwrite moves. On Unix, managed `File.Move(..., overwrite: false)` can check the destination and then perform a replacing rename, overwriting a concurrent winner; it cannot substitute for atomic no-replace publication. No-follow path/handle checks and atomic private directory/file creation must also remain. Best-effort identity does not justify following links, replacing state or exposing it before permissions are applied. Missing native capabilities (including required Linux `statx`), unsupported platforms and failed ownership/permission checks fail closed, never by loosening ACLs/modes. The [profile-state coverage limits](../../../telemetry.md#cli-events) explain unavailable identity, continued command events and why first-run is not a population count.

The public service host-builder signature remains unchanged; its telemetry-aware helper is named `CreateHostBuilderCore` so ASP.NET's name-only discovery remains unambiguous.

## Behavior and validation mapping

| Behavior | Implementation / validation coverage |
| --- | --- |
| Profile creation and repeat use | Strict versioned profile state, safe concurrent publication, random identity reuse/reset and unavailable-state tests. First-run measures saved profile state, not all installs or unique people. |
| One command event | Single real-parser wrapper; completion idempotence, help/version, unknown input, typed failures, cancellation and original-output parity tests. |
| No argument values | Fixed grammar registry; sentinel tests for aliases, assignments, option-looking values, malformed input and positional parameters. |
| Configured database-provider category | Typed closed projection; all six providers, mixed/identical sources, incomplete evidence, provider-changing writes, failure/disable boundaries, deferred launch snapshots, SDK serialization and enabled/disabled CLI file-I/O parity tests. |
| Command diagnostic breakdowns | Configuration context is included even on validation failures with no API ID or engine launch. Duplicate-entity regression, endpoint/cache/auth/host/entity-bucket contrasts, MCP/relationship/policy categories, missing/null/saved provenance, bounded traversal, scope isolation, immutable races and full SDK envelope tests. |
| Installation/API separation | Profile state and compatible API sidecars are separate. Successful creation, lookup-only later commands and multiple/merged-root cases are tested. |
| Sequential launch/usage linkage | Explicit handoff before the engine's first event. Real CLI web/stdio workflows exercise metadata, serving, first success, failure and shutdown; launch intent is not readiness. |
| Export lifetime | Real helper/introspection and delayed-preflight tests verify one command, correct source, no premature `start` completion, and independent sender ownership. |
| Privacy and routing | Common product gate, SDK fake-HTTP envelopes, constant source-IP suppression, ambient enrichment rejection, no customer destination fallback or process-global SDK mutation. |
| Bounded reliability | Main queue 256, three attempts, one-second SDK attempt; 250 ms ordinary CLI drain, two-second engine drain and independent two-second helper drains not joined by the parent. At most 16 launch reservations, eight retained destinations, no event spool. |
| Current main compatibility | Retains ordered MCP metadata/authorization/registry publication, reload serialization, notifications and shutdown. Swallowed registry failures do not claim accepted telemetry epochs. |

The phase-1 refinements are deliberate: synthetic validation rather than production activation, per-profile rather than hardware identity, and creation-time API identity after successful `init`. Public documentation and tests describe those semantics without treating random IDs as anonymous or copied state as evidence of distinct installations.

## Validation limits

- `CliTelemetry` covers parser/handler behavior and shared offline lifecycle, persistence, delivery and SDK serialization. Platform capability skips are not evidence of that platform's behavior.
- `CliTelemetryLocalDb` exercises real `Program.Execute` through service bootstrap with owned LocalDB data, real REST/MCP tools and GraphQL introspection. It substitutes only the sender, installation identity and local transports/lifetime controls.
- Keep these categories separate. Opt into real-host coverage with the explicit combined filters in [Local validation](../../../telemetry.md#local-validation), not by adding the offline `CliTelemetry` category to database-backed fixtures.
- Existing `EngineTelemetry`, `EngineTelemetryLocalDb` and current-main MCP hot-reload tests remain separate regression suites.
- `TelemetryPackaging` is a separate, source-checkout suite requiring an existing solution build. It invokes the real pack target without restore, then checks embedded dependency ranges; it does not assert arbitrary mixed-version binary compatibility. Re-run it when upgrading the SDK because dependency pinning uses its pack metadata hook.
- Local fake-HTTP tests do not prove Application Insights receipt or stored enrichment. Any live validation must use the selected private test destination, exact built artifacts and synthetic activity. No production collection or live cloud test is implied by this implementation.
- SDK-cached cloud-role/component overrides deliberately prevent delivery rather than leak values. Foreign same-destination exporters and arbitrary embedded coexistence remain unsupported in this validation phase.
